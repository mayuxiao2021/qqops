# 运行形态与功耗(QQOps 3.2.0)

这一版回答两个问题:**能不能少占资源?** 和 **能不能更省电?**

做法是三件事:**合并进程**(4 个服务 → 1 个进程)、**按档位调参**(性能/均衡/省电)、
**按需加载**(不用的模块不导入、不查询不读盘)。全部改动都有真机实测数字。

---

## 1. 为什么要合并进程

3.1 之前 QQOps 是四个独立进程:

| 服务 | 模块 | 职责 | 常驻开销 |
|---|---|---|---|
| `qqops.collector` | `collector.py` | OneBot 上报入口(`:8080`)+ 落库 | Python 解释器 + SQLite |
| `qqops.scheduler` | `scheduler.py` | 定时总结/维护/插件定时任务 | 解释器 + 少量内存 |
| `qqops.webapp` | `webapp.py` | 控制台(`:8091`)+ API | 解释器 + 静态资源 |
| `qqops.watchdog` | `watchdog.py` | 体检 + 自愈 | 解释器 |

Android 上每个 Python 进程都要**各自**付一份解释器 + 标准库 + SQLite 的固定成本
(实测约 25 MB),四个进程就是四份。手机上这直接换来两件事:
**后台被系统杀**(内存压力大,`lmkd` 优先杀内存占用高的应用组)
和**待机耗电**(四个进程各有自己的唤醒节奏,系统无法把它们合并调度)。

合并后的形态(`qqops/runner.py`):

```
        ┌──────────────────────── 1 个进程(runner)────────────────────────┐
        │ 主线程: 主管(看门狗角色)                                          │
        │   · 写 beat_watchdog                                             │
        │   · 每 N 秒一轮: 检查各线程 → 不在就退避重启 → 反复崩就熔断         │
        │   · 顺手把调度滴答跑掉(与体检同拍, 少一次唤醒)                     │
        │                                                                  │
        │ 线程: collector(:8080)  web(:8091)  scheduler                    │
        └──────────────────────────────────────────────────────────────────┘
```

- 入口:`python -m qqops.runner`,`bin/qqops start` 在单进程模式下自动选它。
- **线程崩了照样自愈**:主管对每个线程做 `is_alive()` 检查,不在就按
  `Backoff`(10s→30s→90s…)重启,反复崩 → `crash_loop` 熔断 + 记账,
  与多进程模式用的是**同一套**退避/熔断参数。
- **心跳不说谎**:主管只给"真的活着"的线程写 `beat_<服务>`,
  死了的线程心跳会过期 → 控制台立刻显示异常(不会出现"进程在但调度早停了")。
- 子进程一个都不留:单进程模式下 `stop` 只 SIGTERM 一个 pid,没有孤儿。

### 实测(真机,Termux,Android)

| 形态 | 进程数 | 合计常驻内存 |
|---|---|---|
| 多进程(4 服务) | 4 | **104.6 MB** |
| 单进程(runner) | 1 | **27.5 MB** |

**省下 77.1 MB(约 74%)**。合并后四个服务共享同一个解释器与同一份 SQLite 缓存,
固定开销只付一次。多进程模式没有删:`runtime.mode: multi`(或 `qqops mode multi`)
仍然可用,桌面/服务器上进程隔离更抗单点故障。

## 2. 运行形态:`runtime.mode`

| 值 | 行为 | 适用 |
|---|---|---|
| `auto`(默认) | Android → `single`;其它平台 → `multi` | 装完不用管 |
| `single` | 一个进程跑全部服务(`runner.py`) | 手机、低内存、容器 |
| `multi` | 四个独立进程(原形态) | 桌面/服务器,要进程级隔离 |

- 判定:`PREFIX` 含 `com.termux`,或存在 `/system/bin/app_process(64)` → 视为 Android。
- 切换:`qqops mode single|multi` / `qqops mode auto`,控制台**运维 → 资源**页也有开关。
  切换会自动重启实例(先停旧形态 → 等端口释放 → 再起新形态)。
- 单进程形态写清单 `data/run/runner.json`(`mode/pid/services/started/version`),
  多进程形态没有这个文件 —— 状态判断靠 `pgrep` + 端口,两种模式对外状态字段一致。

## 3. 功耗档位:`runtime.power_mode`

| 参数 | `performance` 性能 | `balanced` 均衡(默认) | `saver` 省电 |
|---|---|---|---|
| 调度滴答 `scheduler_tick` | 5s | 15s | **60s** |
| 主管体检 `watchdog_interval` | 30s | 60s | **180s** |
| 控制台刷新 `console_refresh` | 10s | 15s | **60s** |
| 富化(媒体/链接抓取)`defer_enrich` | 立即 | 立即 | **只跑夜间窗口 `02:00-06:00`** |
| SQLite 缓存 `sqlite_cache_kb` | 8000 | 4000 | **1000** |
| 闲聊日志 `log_quiet` | 关 | 关 | **开**(少写盘) |

设计要点:

1. **档位是"节拍",不是"功能开关"。** 省电档下消息照样秒级入库(采集是事件驱动的,
   不靠轮询);变慢的只是"多久看一眼要不要做定时总结/体检",以及非紧急的富化。
2. **富化推到夜间**是省电的最大头:抓图片/视频/链接要联网 + 解码,
   白天攒着、夜里一次做完,手机待机功耗明显不同(`should_enrich_now()` 判定窗口)。
3. **SQLite 缓存跟着档位变**:`Store.conn()` 读 `PRAGMA cache_size=-<kb>`,
   省电档 1 MB 足够(消息落库是顺序写),避免 SQLite 在内存里留大页缓存。
4. **切换即时生效**:改配置 → 立刻重启实例,不需要卸载重装;控制台开关同理。
5. **档位可以临时覆盖**:`qqops power saver` 只改 `runtime.power_mode`,
   `apply_power_profile()` 把档位展开成实际生效值,状态里两个都显示。

## 4. 按需加载(懒加载)

进程合并只是"少一份固定开销";懒加载是"不用的东西不要碰":

| 位置 | 改动 | 收益 |
|---|---|---|
| `webapp.py` | 顶部不再导入 `summarizer/render/media/linkfetch` 等重模块,改成调用点内 `import` | 控制台进程启动只加载 HTTP + 路由;首屏更快,常驻更小 |
| `scheduler.py` | `summarizer` 在 `_run_summary()` 里导入 | 手机不配置模型时,从来没加载过总结链路 |
| `runner.py` | 按 `services` 清单建服务,`watchdog` 角色由主线程兼任(不再单开进程/线程) | 省一个进程 + 一次唤醒源 |
| `core.py` | 无第三方依赖,`json/sqlite3/urllib` 之外的重模块按需导入 | 冷启动快,安装零依赖 |

## 5. 控制台"资源"页

**运维 → 资源**页把上面这些变成可看的数字,接口 `GET /api/ops/resources`:

- 运行形态(单/多进程)、主进程 pid、自身 RSS;
- 当前档位 + 已展开的生效参数(调度/主管/控制台/SQLite/富化);
- 进程列表(pid、RSS、命令行)与合计;
- **合并效果估算**:合并前后进程数与内存对比(`estimate.note`);
- 一键切换形态与档位(`POST /api/ops/power`)——切换后自动重启,页面会提示刷新。

命令行等价物:

```bash
qqops status          # 运行模式 / 档位 / 四个服务 / 资源档
qqops mode single     # 切形态
qqops power saver     # 切档位(别名 qqops lowpower)
qqops doctor          # 含"运行形态 / 功耗档位 / 保活"自检
```

## 6. 实测验收(真机 Termux)

`_probe/tdeploy33.sh` 每次部署跑一遍,关键输出:

```
运行模式: single(配置 single)  档位: saver(省电)
资源档  : 调度 60s / 主管 180s / 控制台刷新 60s / SQLite 缓存 1000KB / 富化 夜间窗口
● collector 端口 8080    ● scheduler    ● web 端口 8091    ● watchdog
【单进程】1 个进程, 合计 27.5 MB
```

- 四服务健康:`collector/web` 看端口应答,`scheduler/watchdog` 看心跳新鲜度
  (窗口按档位放大,省电档 60s 一跳也不会误判超时);
- 端到端:采集口投递 → 落库 1 条 → 重发被去重 → 撤回标记生效;
- 定时任务在单进程里照跑(`scheduler_beat` 持续刷新);
- `qqops doctor` 全绿。

## 7. 已知边界

- **线程级隔离弱于进程级**:一个线程里 `os._exit()`/C 扩展段错误会带走整个进程。
  为此关键线程都套了 `guard` + `Backoff`,并在主管里重启;真要强隔离就用 `multi`。
- **单进程下"某个服务卡死"只能靠心跳发现**:心跳过期即视为异常并重启线程,
  比多进程少一次"进程真的没了"的确定性,所以健康检查以心跳为准而不是 `pgrep`。
- 省电档的富化窗口是**设备本地时间**;跨零点窗口(`22:00-06:00`)也支持。
