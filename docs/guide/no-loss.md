# 消息会不会漏? —— 停机丢消息的实测与「补采」

> 2026-10-12 做的漏消息审计:把 **NapCat 的日志**与 **QQOps 的消息库**按 `message_id`
> 逐条比对,定位每一条没收到的消息到底丢在哪一环;并据此做了「补采」(停机后从 NapCat
> 本地历史回捞)。
>
> 一句话结论:**采集链路本身不丢消息;丢的都在"采集器没在跑"的那段时间** ——
> NapCat 的 HTTP 上报是尽力而为,失败不重试、不排队。现在这个问题可以用一条命令补回来。

---

## 1. 为什么"采集器不在跑"就等于丢消息

```
NapCat ──HTTP POST──▶ collector(127.0.0.1:8080)   ← 只在两者都活着时成立
```

NapCat 的 `httpClients` 适配器**没有重试、没有离线队列**:当 QQOps 没在监听(机器重启、
升级、进程被杀、休眠)时,那一次 POST 直接失败,消息既不会补发也不会进 NapCat 的待发队列。
换句话说是"**我在才收,我不在就永远没有**"。

这不是 QQOps 的 bug,但**是用户感知到的"漏消息"**,必须解决:

| 场景 | 会丢吗 | 说明 |
|---|---|---|
| 采集器正常跑着 | 否 | 审计里没有任何一条"收下了却没入库" |
| 采集器停机/重启中 | **会丢** | 停机期间的上报全部丢失,时长多久丢多久 |
| NapCat 自己掉线/QQ 被踢 | 会丢 | 掉线期间 NapCat 收不到消息,上游就没有 |
| 机器人自己发的消息 | 不丢(本来就不上报) | `reportSelfMessage: false`,库里也不该有 |

---

## 2. 审计方法(可复现)

1. 从 NapCat 日志里抽 `转化为 OB11Message` 行,取出每条消息的 `message_id` / `group_id` /
   `user_id` / `raw_message` / 行时间(日志覆盖 10-09 19:01 → 10-12 18:31,26 个文件);
2. 与消息库的 `(group_id, message_id)` 全集比对,差集就是"日志里有、库里没有";
3. 对差集逐条定性:
   - `user_id == self_id` → 机器人自己发的(NapCat 配置为不上报,不算丢);
   - 内容在库里、只是 id 不同 → 审计口径的假阳性;
   - 落在**采集器停机区间**(某分钟 NapCat 有上报、我们库里一条都没有)→ 停机丢失;
   - 剩下才是"采集器在跑却没收到",再去**采集器自己的 debug 日志**里查这条有没有被收下。

三天窗口(`10-09 19:01 → 10-12 19:07`)的实测结果:

| 分类 | 条数 | 占比 |
|---|---|---|
| NapCat 上报总数 | 18167 | 100% |
| 库里按 id 匹配上 | 17773 | 97.8% |
| **未匹配** | **394** | **2.2%** |
| ├ 机器人自己发的(配置为不上报) | 252 | 1.4% |
| ├ 采集器停机/重启窗口内(NapCat 压根没投递到我们) | 114 | 0.6% |
| ├ 日志覆盖范围外(装 QQOps 之前) | 27 | 0.1% |
| └ 采集器收下了却没入库 | **0** | **0%** |

这条曲线本身就是「补采」的价值:最早按 id 比对时未匹配 1046 条(5.9%),补采把停机窗口
能拿回来的都拿回来了,残留 394 条(2.2%)—— 而其中 252 条是**按设计就不该有**的
机器人自己的消息、27 条发生在装 QQOps 之前,真正"漏了"的只有 114 条(0.6%),
全部落在停机/重启窗口里(NapCat 本地历史也已经被清理到够不着的部分)。

> 结论:**"收下却没入库" = 0 条**。运行期采集链路没有丢消息;所有丢失都发生在采集器
> 不在跑的时候,而这类丢失现在可以补回来。

## 3. 「补采」:把漏掉的从 NapCat 历史里捞回来

NapCat 本地保留着聊天历史(`get_group_msg_history` / `get_friend_msg_history`),
所以恢复后可以按 `message_id` 把缺口补齐:

```bash
qqops backfill                      # 补最近 12 小时(配置 collector.backfill_minutes)
qqops backfill --minutes 720        # 指定窗口
qqops backfill --dry-run            # 只统计不落库, 先看看能补回多少
qqops backfill --deep --minutes 9000 --pages 60    # 深挖: 连夹在中间的老空洞一起修
```

控制台:**运维 → 存储 → 停机补采**(可填窗口、勾选「深挖」、先试运行)。

行为要点:

- **自动**:单进程/多进程启动后各会自动补一次(受 `collector.backfill*` 配置控制);
  空档小于 `backfill_min_gap`(默认 45 秒)的会话不扫,重启两秒不值得扫全群。
- **幂等**:入库复用采集器同一条路径,`(group_id, message_id)` 唯一索引去重 ——
  重复补采不会写重,也不会覆盖已经修正过的内容。
- **克制**:日志覆盖范围外(装 QQOps 之前)的历史,只有 `--deep` 且落在窗口内才会被拉进来;
  默认窗口 12 小时,不会把陈年旧账灌进库。
- **如实报告**:页数/超时封顶时,结果里会写"未够到底",不会假装补全了。
- **NapCat 挂了就跳过**:拿不到 API 就明确报错退出,不影响采集。

### 翻页口径(NapCat 实测)

| 参数 | 效果 |
|---|---|
| 不传 `message_seq` | 返回**最新** `count` 条(老→新) |
| `message_seq` + `reverseOrder: true` | 返回**比它更早**的一页 |
| 只传 `message_seq` | 无效(原样返回最新一页) |
| `count` 上限 | 实测 1000 仍能返回,超过按 1000 处理 |

补采模块已经把口径封装好了:见 `core.NapCat.group_history(group_id, count, message_seq, reverse)`
与 `core.NapCat.friend_history(user_id, count, message_seq, reverse)`。

## 4. 自查方法

```bash
# 手动补采一次(先试运行看能补多少)
qqops backfill --dry-run --minutes 720

# 看补采明细(每个会话翻了几页、最老到哪、是否够到底)
grep '补采' ~/qqops/data/logs/backfill.log | tail -n 30
```

控制台「运维 → 存储」里能看到上次补采的时间和补回条数;「采集指标」里的
`收下/跳过/拒绝/错误` 是采集器本次启动以来的累计。
